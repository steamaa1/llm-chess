# 《LLM 象棋》实施计划

生成日期：2026-07-31。项目根目录在 `/workspace/llm-chess`；该目录目前是空目录且**尚未初始化 Git 仓库**，因此计划中的漂移基线为“初始空目录”，没有可填写的 Git commit SHA。

## 已确认的产品决策

- 交付形态：响应式 Web 应用 + PWA。
- 模式：① 观看 LLM 分别操控红、黑双方对弈；② 玩家与 LLM 对战。
- 模型接入：用户自带 API Key；红黑方可分别配置模型/Key，默认从一方复制到另一方。
- 接口范围：OpenAI Chat Completions 兼容接口；首版实际兼容验收 OpenAI、DeepSeek、SiliconFlow，并允许自定义兼容 Base URL。
- 密钥原则：只在浏览器当前会话内存和单次 HTTPS 请求中存在；后端只转发，不写数据库、文件、日志、LocalStorage 或棋谱。刷新页面后必须重新填写。
- 裁决原则：确定性中国象棋规则引擎是唯一裁判；LLM 只能在引擎给出的合法着法中选择。LLM 的“走棋说明”是公开短评，绝不是隐藏推理过程。
- 选着协议：每回合向 LLM 提供局面摘要、近况与合法着法，要求严格 JSON 返回一个候选着法；服务端再次校验。解析/校验失败仅有限重试，绝不自动臆测走法。
- 首版功能：基础可玩版（人机、LLM-vs-LLM、暂停/继续/单步/速度、悔棋、重开、走棋说明、棋谱列表、导入导出）。不做局面编辑、残局库、传统引擎评估、最佳着法或自动复盘。
- 数据：无账号、无云端数据库；棋谱及非敏感设置保存在本机浏览器。棋谱使用带 schema 版本的 JSON 导入/导出，并可导出纯文本中文棋谱。
- 对局上限：默认 200 回合（400 半回合），用户可选 50–400 回合。达到上限显示“达到对局上限，未判胜负”，不能擅自判和。
- 界面：仅简体中文；“传统中式棋盘 + 现代简约控制台”。
- 目标部署：香港 1G LXC VPS，不能 Docker。用户明确要求本计划不处理服务器到模型 API 的网络可达性；这不等于该风险不存在，实际部署/验收时若不可达，模型功能会失败。

## 推荐技术栈（本计划的执行前提）

| 层 | 选择 | 原因与边界 |
|---|---|---|
| 前端/PWA | React + TypeScript + Vite + `vite-plugin-pwa` | 产物可静态托管、开发反馈快，适合 1G VPS；PWA 仅缓存前端壳和静态资源，不缓存 API Key 或模型响应。 |
| 后端 | Node.js + TypeScript + Hono | 轻量 HTTP 服务，负责 API Key 的瞬时代理、请求契约、限流/超时和模型响应验证；不使用 Docker。 |
| 棋规 | 经过测试、明确支持中国象棋的 TypeScript 规则库；若审查发现其规则/许可/维护状态不达标，则在计划 002 的评估门槛处停止并替换 | 不能自行用 LLM 或不完整手写规则充当裁判。库选择必须先以合法走子、将军、将死、困毙、重复局面/和棋能力和许可证验证。 |
| 共享契约 | TypeScript workspace 内的 `packages/shared` + Zod | 前后端共用局面、棋谱、请求/响应 schema，避免 API 漂移。 |
| 测试 | Vitest（单元/组件逻辑）+ Playwright（关键浏览器流程） | 不把真实模型 API 调用纳入 CI；以可控 mock 服务器覆盖协议。 |
| 部署 | systemd 运行单个 Node 进程，已有反向代理终止 HTTPS；Nginx/Caddy 的选择留待 VPS 实况确认 | LXC 不能 Docker；构建在 CI 完成，VPS 只接收构建产物与生产依赖。 |
| CI | GitHub Actions 构建、类型检查、测试、打包产物 | 与“低内存 VPS 不在生产机构建”一致。 |

> **尚未确认、且会阻塞真实上线的部署输入**：域名、现有反向代理（1Panel/Nginx/Caddy）、Node LTS 版本、可用内存/Swap、服务运行用户、TLS 证书方式、开放端口，以及模型 API 网络连通性。计划 005 要求在改 VPS 前逐项核对；不能根据猜测执行。

> **技术栈变更记录（2026-07-31）**：执行 Plan 001 前已检查环境：Node.js v22.23.1、npm v10.9.8 可用；没有 pnpm 命令、pnpm store 或项目依赖。操作者选择使用现有 npm workspace，故原先“pnpm workspace/命令”统一替换为 npm workspace/等价 npm 命令；产品、架构与安全约束不变。

## 已考虑但不纳入首版的事项

- **模型隐藏思维链展示**：不可靠且不应索取；仅显示模型按模板生成的简短走棋说明。
- **传统象棋引擎评估/最佳着法/复盘**：与“LLM 下棋”是不同能力，需单独引擎、标定与产品设计，首版不做。
- **账户、云同步、多人房间**：会引入身份、数据库、隐私和滥用防护，超出首版。
- **无上限自动对弈**：会产生不可预期费用；已用最大回合数约束。
- **处理 VPS 到各模型服务的网络问题**：用户明确排除；部署失败时应如实报告，不能静默降级或伪造走棋。

## 执行前通用约束

1. 执行者不得把真实 API Key 写入代码、测试夹具、截图、日志、LocalStorage、棋谱、Git 历史或错误报告。
2. UI 和 API 都不得把“模型短评”称为“思维链”“推理过程”或“真实思考”。
3. 非法模型输出、网络失败、超时、429、供应商 5xx 必须保留棋局不变并给出可恢复的中文错误状态。
4. 每次代码修改后，必须实际运行该计划的测试与检查，全部通过后才能交付或推送。
5. 本项目初始化 Git、安装依赖、创建远程仓库或推送前，遵守操作者当时的授权与项目 Git 约定；本计划不授权这些操作。

## Findings considered and rejected

- 无既有源码可审计：这是空项目的设计规划，不把“没有测试/没有 README”作为已有代码缺陷。
- 纯静态前端直连模型 API：拒绝。它无法一致处理 CORS/响应契约，且使 API Key 暴露面更大。
- 将 Key 保存到 LocalStorage 以便刷新后恢复：拒绝。便利性不值得持久化高敏感凭据的风险。
- 由 LLM 直接判定走法和终局：拒绝。规则正确性必须由确定性引擎保证。
