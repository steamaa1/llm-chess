- **计划时间**：Plan 001 完成后填写其 commit SHA，2026-07-31

## 为什么重要

LLM 会生成错误、含糊或不合规则的内容，不能充当裁判。本计划建立唯一可信的中国象棋领域层：棋局状态、合法走法、中文记谱、将军/将死/困毙/和棋与回退。之后的 LLM 网关与 UI 只能调用这一层，绝不可自行判断落子合法性或终局。

## 当前状态

- Plan 001 建立 `packages/shared/src/game.ts`，其中只有 `GameMode`、`Side` 和版本化棋谱骨架；本计划将扩展它。
- 前端在 `apps/web`，API 在 `apps/api`；共享棋局逻辑必须进入 `packages/shared` 或新增受该 package 控制的 `packages/xiangqi-core`。推荐新增后者，避免 UI/API 直接持有第三方规则库。
- 产品规则：标准中国象棋开局；默认上限 200 回合（400 半回合），可设 50–400；达到上限的状态是“达到对局上限，未判胜负”，不是和棋。
- LLM 只能从本模块返回的合法着法中选；“走棋说明”不参与任何规则计算。

## 步骤

### 第 1 步：选择并锁定棋规依赖前做准入评估

调研候选 TypeScript/JavaScript 中国象棋规则库，但**不要先安装多个候选**。将评估结论写入 `README.md` 的“规则引擎”小节或 `docs/decisions/001-xiangqi-engine.md`。至少核对：

1. 明确支持标准中国象棋全部棋子、九宫、马腿、象眼、炮架、兵过河规则。
2. 能针对任意合法局面返回合法着法，而非仅返回伪合法着法。
3. 能正确区分将军、将死、困毙；对重复局面/长将/长捉规则的支持程度必须有证据。
4. 有适合商用/开源项目的许可证，维护状态可接受，且能在 Node 与浏览器构建。
5. 可从标准初始局面及一个可序列化局面恢复状态。

**验证**：在决策文档中列出选定库、版本、许可证、上述五项的依据及已知限制。若库无法满足 1–3，或许可证不清楚，停止，不得继续接入。

### 第 2 步：建立引擎适配层和稳定领域模型

1. 创建 `packages/xiangqi-core`，其唯一职责是封装选定库；不让 `apps/web`、`apps/api` 或 `shared` 直接导入第三方库。
2. 设计不可变/可复制的 `GameState`：至少包括版本化局面编码、轮到哪方、半回合数、历史走法、终局状态和重复判定所需历史信息。所有外部输入均通过 Zod schema。
3. 对外只公开：`createInitialGame`、`restoreGame`、`getLegalMoves`、`applyMove`、`undoMove`、`getGameStatus`、`toRecord`。`applyMove` 只能接受本局返回的稳定 `moveId`，并在内部再次验证；非法 ID 返回结构化领域错误且原状态不变。
4. 设计 `LegalMove` 至少含稳定 `moveId`、起止坐标、标准中文着法、走后是否将军。不要把展示名称当作唯一标识，因为同名/歧义记谱可能存在。
5. `GameStatus` 至少区分：`in_progress`、`red_wins_checkmate`、`black_wins_checkmate`、`red_wins_stalemate`、`black_wins_stalemate`、`draw_repetition`（仅在引擎能可靠判定时启用）、`move_limit_reached`。将“困毙”胜负归属按中国象棋规则明确测试。
6. 在 `packages/shared` 中定义版本化 `GameRecordV1`：初始局面、模式、参与方非敏感模型显示名（绝不含 Key/Base URL）、走法数组、每步公开短评可选字段、结果、创建/完成时间、规则配置（含最大回合）与 schemaVersion。导入必须拒绝未来未知版本及不完整/非法记录。

**验证**：`pnpm typecheck` 退出码 0；为每个公开函数至少写一个输入/输出契约测试。

### 第 3 步：建立棋规回归测试矩阵

以明确、可审查的局面夹具覆盖以下类别。夹具必须说明局面来源、轮到谁和预期，而不能只用随机对局：

- 初始局面：红方先走，合法着法非空。
- 每种棋子至少一个合法移动与一个非法移动：车、马（马腿）、相/象（象眼与不过河）、仕/士（九宫）、将/帅（九宫与将帅照面）、炮（无架/单架/多架）、兵/卒（过河前后）。
- 双将/将帅照面、己方将帅暴露、被将军时只能应将。
- 将军、将死、困毙分别正确识别。
- 同一局面/同一走子序列的合法着法与 `moveId` 稳定；非法 moveId 不改变状态。
- `undoMove` 后局面、轮次、历史与合法走法完全恢复。
- 回合阈值 50、200、400；达到上限只得到 `move_limit_reached`。
- 棋谱 JSON：有效记录可往返（导出再导入），损坏版本、非法走法、包含疑似密钥字段的额外内容均被拒绝或剥离；不记录 Key。

若选定库不能提供重复局面判定，测试必须将其标为不支持，产品 UI 不得声称已按正式竞赛规则判和；记录该限制并暂停 `draw_repetition` 的公开暴露，直到有可靠实现。

**验证**：`pnpm test --filter xiangqi-core` 通过，且测试报告中每个上列类别至少有一条命名测试。

### 第 4 步：定义中文记谱与显示边界

1. 统一界面显示为标准中文着法；选定引擎若不能提供，适配层负责从坐标及局面生成，但须用测试夹具验证歧义消解（前/后/中、进/退/平）。
2. 对 LLM 的合法走法输入，传递 `moveId` 和中文 `notation` 对；要求模型返回 `moveId`，而不是只返回自然语言记谱。
3. 棋盘方位、红黑命名、回合编号、历史排序全部在领域层定义并有单元测试；UI 只能渲染。

**验证**：测试中至少包括两个同类棋子可能歧义的局面；输出不可为空，且同局面重复运行一致。

## 测试计划

- 单元：上述全棋子规则、应将、终局、回退、上限、序列化。
- 属性/序列测试（如工具链允许）：从初始局面随机选合法步进行有限长度对局；每一步应用后轮到对方、局面可恢复且不会产生将帅照面。随机测试必须固定 seed 以保证 CI 可重复。
- 契约：共享 `GameRecordV1` 不接受 API Key、Base URL、Authorization、token 等字段。
- 不写依赖真实 LLM、真实 API 或视觉点击的测试；这些属于后续计划。

## 停止条件

- 没有一个候选库可证明满足标准走法、终局或许可证要求。
- 为支持引擎而不得不把其未经验证的内部状态直接写入长期棋谱。
- 发现重复局面/长将规则不能可靠支持，却被要求对外宣称“完整竞赛规则和棋裁决”。
- 测试揭示选定库会允许将帅照面、己方被将或非法移动。
- 引入新依赖未获得操作者许可。

## 维护说明

- 规则引擎升级必须先跑完整回归夹具；任何走法/记谱变化都可能使旧棋谱不可回放。
- `GameRecordV1` 一旦发布不得破坏性改字段；未来变更用 `V2` 和显式迁移。
- 长将/长捉等赛事细则与“重复局面”不是同一概念；若产品以后承诺赛事级规则，必须单独设计、实现并审查。
- Plan 003 只能使用 `getLegalMoves` 的 `moveId`；Plan 004 只能从领域状态渲染，不能在 UI 内重算规则。
